# Airside

A sandbox/tycoon airport builder for PC, prototyped in the browser. The look is a top-down airport-diagram print, with a 3D view styled like a presentation model.

The player draws runways, taxiways, roads and sidewalks, and blocks out terminal modules on two levels: check-in, security, concourse, bag claim, curb and parking. The game fits each module out procedurally. Aircraft, passengers, bags and cars then flow through what was built. Every failure should be fixable with staff, space or layout.

README.md has the full feature list, controls and known gaps. Keep it current.

## Commands

```
npm install
npm run check        # TypeScript type-check
npm run build        # dist/index.html, one self-contained file
npm run dev          # rebuild on save
npm run simtest      # 3 sim days on the sample airport, prints the daily report
node scripts/terminals.mjs   # multi-terminal scenarios
node scripts/stress.mjs      # 14 days with deliberate cuts and an A380 build-out
node scripts/growth.mjs      # every growth facility, international flights, the AirTrain
node scripts/roads.mjs       # curves, roundabouts and one-way loops
node scripts/halls.mjs       # stacked halls and self-laid forecourts
node scripts/satellites.mjs  # satellite concourses and people movers
node scripts/piers.mjs       # piers at any angle and round or polygonal hubs
node scripts/aprons.mjs      # self-laid aprons and taxilanes, and reshaping by grips (exits 1 if a check fails)
node scripts/curves.mjs      # bent and tapered piers (exits 1 if a check fails)
npm test             # all ten sims
node scripts/livedrag.cjs    # drives the built page with the mouse: gates follow a taxiway as it is dragged, a runway's end stretches live, a building is moved by its roof in 3D, and a satellite is drawn in 3D (needs playwright and a build; not in npm test or CI; exits 1 if a check fails)
node scripts/shot.cjs out.png <camX> <camY> <zoom> ["js using g = window.__game"]   # needs playwright; GL3D=1 for shots of the 3D view
```

## Architecture

- **One file out.** scripts/build.mjs bundles src/ with esbuild into a single HTML page. There is no server. Two runtime dependencies are bundled in: three.js (pinned 0.170.0), used by render3d.ts alone, and clipper-lib (polygon union and offsetting), used by shell.ts alone.
- **The sim never touches the DOM.** config, geom, net, ways, shapes, terminalplan, world, gates, bands, commerce, frontage, roads, scenery, goals, layout and sim are pure logic.
  - render.ts (plan) and render3d.ts (3D, three.js, with models3d.ts) read sim state and never write it. traffic.ts is pure too.
  - scenery.ts places trees, lamps, floodlight masts and the control tower from the layout (cached per derive); both renderers draw from it.
  - ui.ts owns input and panels.
  - Keep this split: sim and world may be ported to Godot/C# later.
- **World vs derived.** `World` (world.ts) is the saved, player-built state: zones, runways, ways and terminal sites. `derive(world)` rebuilds everything else after any edit:
  - generated curbs and upper decks (frontage.ts); `d.zones` is the world's zones plus these, and is what the sim and renderers iterate
  - designators
  - gates and aprons
  - the airfield, road and pedestrian graphs
  - vertical cores and crosswalks
  - terminals
  - fit-out frames
  - design-check issues
- **Networks** (net.ts): drawn segments are split into graphs at intersections. Routing uses Dijkstra and all-pairs.
  - Airfield edges carry a class. Back-taxi on a runway is allowed at ×4 cost.
  - Pedestrians move only through doors where same-level zones touch, through vertical cores, and along sidewalks.
- **Aircraft classes** (config.ts `CLASSES`): turboprop, regional jet, A320, A380. Each sets runway length, gate spacing, stand depth, seats and turnaround.
- **Terminal sites** (v0.8): `world.sites` are allocated with New terminal (an empty site by default since v0.19; the starter layout is an option); each module carries `site`.
  - A terminal is a site plus the modules on it. A module with no site joins the site of whatever it connects to on foot.
  - v0.15: terminalplan.ts (pure) gives a new site its starter layout: `airsideOf()` picks the edge facing the nearest taxiway or runway, `planTerminal()` returns the concourse, security and hall rectangles. ui.ts `buildSite()` builds them unless the tool is set to Empty site, and hires staff for a second terminal.
  - The UI places terminal modules only in the open terminal, then calls `fitSite()` so the site grows to fit.
- **Levels of detail** (v0.8): `ren.lod` is `airfield`, `landside` or `terminal`, and `ren.focus` is the open site.
  - ui.ts switches them by zoom (`LOD` in config.ts) or explicitly. Each tool declares its level.
  - render.ts and render3d.ts decide what to draw from them. The sim doesn't know about them.
- **Frontage** (frontage.ts, v0.8): a road parallel to a check-in, claim or security face within `FRONTAGE.minGap`–`maxGap` grows a curb.
  - The curb is a Zone with a negative id and an `auto` tag, rebuilt on every derive and never saved.
  - L1 departures over L0 arrivals on the same road make a `dep` curb at L1, an `arr` curb at L0 and a `DeckSpan`.
  - Roads are split at curb ends so cars can pull in. The sim prefers `dep` curbs for drop-off and `arr` for pickup.
  - v0.12: `autoForecourt()` runs first. A check-in hall (with whatever claim is stacked under it) that no drawn road fronts lays a frontage road at `FRONTAGE.ideal` off its best open face and a link from each end to the nearest road within `FRONTAGE.reach` (straight out, straight on, or since v0.14 out and round one corner). These are generated `Way`s with `fore: 'face' | 'link'` and ids above `FORE`; they join `d.autoRoads`, and `autoFrontage()` grows curbs and decks on the `face` one like on any road.
  - v0.13: each forecourt link that comes straight out also gets a `fore: 'ramp'` way (curved, `face` = its frontage road's id): it leaves the link and lands on the frontage line. `DeckSpan.pts/zs/ws` is the deck's whole path with height and width per point; both renderers draw the deck from it. `d.rampRefs` lists ramp ids: the sim routes only deck trips over them (`roadDJ(target, deck)`), and roads.ts and `sim.roadCap` treat a ramp's ends as merges, not junctions.
  - v0.27: render.ts draws the deck with the ground roads' surface and markings and a shadow offset by height, and skips ramp paths on the ground (`groundPaths`); render3d.ts builds the slab at the true widths. v0.30: render3d.ts also draws the deck's lines (edge lines off the `abut` sides, lane lines, the double centre line) at the deck's height point by point, and the seams, gores (clipped chevrons, `segT`) and lane arrows on the ground.
  - v0.28: ramps are parallel-type ramp terminals. In `autoForecourt`, a link that comes square out of the frontage gets a `RampGeo` (world.ts): along the link from the frontage corner, the nose N (`RAMP.nose`), the end of the speed-change lane P (`RAMP.lane` further) and the end of the taper T (`RAMP.taper` further, on the link's centreline), all scaled down on a short link (to a 45 m nose and 20 m lane and taper), and T is kept `RAMP.clear` short of the link's far end and of the outer kerb of a roundabout there. A straight deck ramp (no ramp of its own) lands within its own road. The world.ts loop that joins road ends to the highway skips ramp pieces. The lane runs `h + DECK.lane / 2` off the link's centreline, on the side nearer the terminal; the curve from N to D (on the frontage road, `RAMP.along` from the corner) is a cubic (handles `RAMP.leave` / `RAMP.arrive`) carried as two quadratics through its middle M. It is emitted as four one-way `fore: 'ramp'` ways (`part` taper, lane, curve, climb; ids `RAMP_ID + hall id * 16 + ramp * 4 + k`), up or down by traffic keeping right (`rg.up`: the ramp is on the right of inbound traffic); the curve way carries `rg`. `autoFrontage` builds each end of the deck from `rampLine(rg, W)`: the taper and lane at grade along the road's edge, then the curve, level until `GORE.climb` clear of the road and climbing after, with `abut` (which edge is the road's), the gore polygon, the seam and lane arrows on the `DeckSpan`. `autoRoads` never attaches a drive to a ramp. traffic.ts centres cars on a one-lane one-way edge.
  - v0.28: where a link comes square out of an end of the frontage road, `autoForecourt` cuts both back by `CORNER.radius` and adds a curved `fore: 'corner'` way between them (control point at the old corner; ids `RAMP_ID + hall id * 16 + 12 + i`). It is an ordinary curved road to the network and to `roadPlan`.
  - v0.29: halls turn. `TURNABLE` (world.ts: checkin, claim, security, passport) can carry `rot`. They keep the four edge grips (`canTurn` stays false for them, so `regrip` uses the edge rules, in the turned frame) and `gripsFor` adds a turn handle `t` off the end of the long axis: `regrip` turns about the centre in `snapDeg` steps and, square to the grid, returns an upright rectangle (no `rot`), so shared walls work again. `canPlaceTurned` lets a turned one overlap other terminal modules on its level (not another hall, a lot, a taxiway on any level, a non-self apron, or a road or roundabout at ground level), and ui.ts `placeGeom` adds the same site rules as an upright module (`siteRules`); `fitSite` grows a site by a turned module's `zoneBox`. layout.ts `touchLen` ignores neighbours on the other level for turned edges, and frontage.ts `blocker` tests turned ground-level zones by their outline. ui.ts `liveSet` copies the whole shape, angle included, to the twin. layout.ts `edgesOf` turns a module's edges and `touchLen` tests a turned edge (or a turned neighbour) by sampling just outside it, so every fit-out frame turns with its module. frontage.ts: `faceBox` (a turned `quad` off a turned face, else the old bounding box) for the interior-face and lot probes; a turned face's curb is a turned zone reaching 0.5 m into the hall (`quad(..., -0.5)`), so derive joins them by overlap (the shaped branch now handles curb pairs: doors along the overlap, frontage stairs where the hall is above); `curbCuts` and road attachment (`inZone`) read turned curbs. `autoForecourt` also tries, from a turned face only, a link straight to the nearest point of a road within 45° of straight out (out to 1.25 × `FRONTAGE.reach`), and builds ramps (`rg.u` along the link, `rg.n` across it) and corner curves on links up to 45° off square. render3d.ts `massing` turns every box of a turned non-concourse module about its centre, and the curb's strips and canopy are turned boxes. Upright halls are laid out exactly as before.
  - v0.34: halls bend. `BENDS` (world.ts: checkin, claim) can carry `bend`, as a pier does (x, y, w, h and `rot` the chord's frame). `gripsFor` gives an upright or turned hall a bend grip `m` in its middle; a bent one gets a pier's grips less the taper ones (`a`, `b`, `n`, `s`, `m`) and the turn handle. `regrip` 'm' with `turns` false returns an upright rectangle when pulled straight within 1e-3 of square to the grid (an end grip leaves a bent hall at `rot` 1e-4), and 't' keeps a bent hall's length on its own x; its turn handle stands off the end of the chord. `canPlaceTurned` and ui.ts `placeGeom` take `bend`; `liveSet` copies it to the twin; `migrateWorld` keeps it on halls. layout.ts `layoutZone` lays a bent hall out on `frameOf(z)` with its neighbours boxed in that frame and carries every item, slot and the frame's ends through `toWorld`. frontage.ts `facesOf(m)` is `sidesOf` with each curved wall cut into straight pieces (as many `FACE_PIECE` m pieces as that wall's own length holds), each a face with `chain` (the wall), `k`, `sag` (how far the wall stands off the chord) and an `out` taken from the frame (away from the building's middle), not from a probe. `autoFrontage` grows curbs on each piece from two thirds of `FRONTAGE.minLen` of shared run (a piece takes the one road chord it shares most with); a piece's curb is a turned quad reaching `0.5 + sag` into the hall, with an id of its own (`-(1e13 + base * 64 + k)`), and carries `auto.chain` / `auto.k`. One deck runs along the whole chain, built with the first piece, through the pieces' joints (`mids`), with `roads` listing every chord (traffic.ts finds a car's deck by it); ramps are found by forecourt (`FACE_ID` block), not by chord. The "drawn frontage" early-out tests `facesOf` pieces. `blocker` tests every shaped ground-level zone by its outline. roads.ts treats consecutive chords of one forecourt as one road (`sameRoad`). ui.ts `placeGeom` refuses a bend or reshape of a hall that loses its overlap with a terminal module it touched when the drag began. `autoForecourt` lays a curved face's frontage road as a chain of chords through the wall's joints carried out along the wall's normal there, straight on past each end (generated `fore: 'face'` ways, ids `FACE_ID + hall id * 32 + i`); links, corner curves and ramps attach at the chain's ends as on a straight face, each ramp tied (`face`) to the nearest chord that fronts the hall. Curb pieces carry `auto.chain` / `auto.k`; render.ts names a chain once, on its middle piece. Straight faces are laid out exactly as before.
  - v0.39: drawn curved roads front a face. `opposite(r, sd, L, al, memo)` (frontage.ts) gives, for a curved road, the longest run of its chords between the face's two ends as one straight `Way` (same id, no `c`) if the curve stays within 3 m of that line, else null; a straight road is itself. `autoFrontage` tests every drawn road through it (one object per road and face, memoised, so the hall's two levels share it for `ground()`), and `realOf` maps it back: where the deck is over a curved drawn road, `bendEnd` brings each end down along the curve (`FRONTAGE.ramp` of it, through its joints) instead of straight on, and over a straight face its middle follows the road's joints. ## Conventions

- One version per pull request. Bump `version` in package.json and the README heading's feature list. Update known gaps. Describe changes in plain language.
- Before opening a PR, run check, build and all the sims (`npm test`). Take a screenshot of anything visual.
- Use real planning numbers (ACRP, IATA, ACI) where they exist, and cite them in a comment where the constant lives.
- The owner is an architect. Plan language (frontage, bands, holdrooms, cores) is welcome; game-design jargon less so.

- Construction is instant.
- Departing bags aren't simulated.
